Batched Code Review and Release Assessment

Implementation specification version 3 · November 1, 2026

Status: implementation specification version 3 Date: November 1, 2026 Audience: implementation agent and project maintainer Working executable name: reviewd

1 Purpose and authoritative decisions

Build a self-hosted Go service inspired by PR-Agent. Host code assembles a bounded context package and submits one batched prompt for each PR review. The model returns a structured review and a 1–10 merge-risk estimate in that same response. Go code validates the result and enforces approval minimums.

Repository context is maintained separately. Every merged PR or MR must be incorporated into an append-only change journal, whether or not this service reviewed or approved it. Periodic context builds compact accumulated changes into a new immutable base snapshot. A pre-release mode assembles the base context, release-range journal entries, exact changes, and operational evidence into one batched release assessment for the release engineer and a draft release-channel update.

These decisions supersede the first design:

  • One logical model request per review. No model tools, read-only exploration loop, agent turns, adaptive retrieval, or automatic per-file/chunk review calls.
  • All source gathering and selection happen deterministically before inference.
  • A 1–10 merge-risk estimate is part of the review response; user-configured thresholds and deterministic risk floors govern approval eligibility in Go. No second approval model call.
  • Every merge is journaled; scheduled compaction does not replace merge ingestion.
  • Pre-release assessment is a first-class mode with its own scope, input budget, schema, deterministic risk minimums, and reports.

Use PR-Agent's behavior as a reference, not a requirement for complete feature parity. Deliver an implementation rather than a general agent framework. Start with the vertical slice in Section 18.

2 Scope and outcomes

Required: GitHub/GitLab adapters; immutable revision identities; independently maintained snapshots; merge ingestion and recovery; deterministic context packing; one batched PR review; approval enforcement; one batched pre-release assessment; structured records and readable reports; strict token and cost limits; offline fake-model tests.

Excluded initially: autofix, code writes, automatic merges, deployment execution, model-callable tools, arbitrary shell execution, cross-repository analysis, embeddings, a web dashboard, and outbound release-channel messaging. The system generates a channel-ready draft. It does not post it without a separately authorized integration.

The host may perform bounded source reads and index lookups during assembly. The model cannot request additional context. If the assembled input is insufficient, the model must return questions or human_required; it cannot initiate further work.

Default approval mode is shadow. Default PR mode reviews the complete current PR diff. Reuse an identical completed review when its full input identity matches; defer partial-PR coverage reuse until measured and independently specified.

3 Architecture and execution flow

One binary exposes CLI commands and a durable worker. Shared storage is SQLite plus a content-addressed artifact directory.

Execution relationships:

  1. Schedule → build base snapshot.
  2. Each merge → journal actual integrated changes and invalidate affected context.
  3. PR event → assemble snapshot plus compatible journal plus exact diff and evidence → one model response → deterministic approval gate.
  4. Pre-release request → assemble release baseline, candidate, snapshot, journal, net diff, checks, and operational evidence → one model response → apply risk minimums and render release reports.

Readers pin published artifacts. Builders and ingesters write new artifacts atomically; they do not mutate a context package used by a running review. The reviewer has no publishing credential. Only host publishing code can approve. Context-building and release-assessment components cannot approve PRs.

4 Revision model and invariants

Capture repository/source-repository IDs, PR/MR identity, head_oid, target_oid, merge_base_oid, head tree, snapshot commit, journal cutoff, policy/instructions digests, and engine/prompt/model/schema versions. Treat object IDs as opaque validated IDs; do not assume a fixed hash length.

Review the diff from merge base to HEAD. Before-images come from merge base; after-images and supplementary source come from HEAD. Record target separately. Fork source identity must be explicit. Under the initial approval policy, target must be an ancestor of HEAD; otherwise review can proceed but automatic approval is withheld. Synthetic merge/queue-tree review is deferred.

Select a snapshot compatible with the reviewed tree. For an older branch, use an ancestral snapshot plus journal entries from its actual ancestry, not all entries from today's target. Apply current PR changes as an ephemeral overlay to invalidate or replace stale summary claims before packing. Never append unmerged PR changes to the shared journal. If compatible context cannot be materialized, use bounded exact source context and mark the limitation.

Invariants:

  • Every source read is pinned to a repository and immutable revision.
  • Model output cannot establish coverage, waive policy, or create approval authority.
  • Input omissions, stale context, unavailable evidence, malformed/truncated output, and missing checks are explicit states.
  • A successful response proves protocol completion, not semantic understanding of every supplied line.
  • Shared journal entries describe merged target-branch state; review findings describe what a reviewer observed. Neither is a substitute for the other.
  • HEAD, target, policy, or check changes invalidate affected eligibility decisions.
  • Release risk and readiness are separate: low estimated risk does not imply complete evidence or readiness.
5 Independent base context preparation

Build repository inventory, module map, Go declarations/import index, dependency metadata, bounded module summaries, and context-health metadata. Record each artifact's source blobs, dependency blobs, generator version, prompt/model identity if generated, and configuration digest. Go syntax/import indexing uses the standard library initially; other languages use bounded text and manifest extraction. Do not claim a complete call graph.

Snapshots contain an overview and references to selectable module artifacts. They are not necessarily included wholesale in every request. The assembler chooses relevant artifacts before inference. Summaries are derived claims; source is authoritative.

Build on a configurable schedule and optionally on invalidation/size thresholds. Every merge still creates a journal record immediately; a merge may additionally request a background refresh. Full-repository summarization is never a prerequisite for each PR review. Background summaries use fixed bounded batches, without tool loops, and have budgets separate from online reviews.

Write content by SHA-256 digest, verify it, then transactionally publish the snapshot and active pointer. A failed build leaves the previous snapshot intact. Coalesce redundant builds with durable leases. Compaction creates a new snapshot through an explicit target commit and links the journal entries it incorporates.

Compaction does not erase release history. Retain journal records and source references needed by active runs, configured release baselines, and the audit retention window. Missing retained data must be visible to release assessment.

6 Every merged PR enters the journal

Ingestion trigger and identity

Consume authenticated merge events and periodically reconcile forge merge history and actual tracked-branch Git history. Webhooks alone are insufficient. Ingest merges even when the PR was unreviewed, manually approved, or merged while the service was unavailable. Review success is never an ingestion prerequisite.

Uniquely identify a merge integration by provider, repository, target branch identity, PR/MR ID, and actual integrated commit/range. Duplicate events are idempotent. A later metadata enrichment is a new revision of that record, not a second application of the code change. The same PR cherry-picked onto another branch is a distinct integration with an explicit relationship if known.

Git truth and PR attribution

Separate the canonical target-branch transition ledger from PR attribution records. Walk actual branch history in ancestry order. Each integrated commit/change is accounted for once. For merge commits, use the first-parent transition to capture the integrated tree change, including conflict-resolution edits. For squash/rebase/fast-forward integration, resolve actual target commits/ranges through provider evidence and Git verification. Do not use the original PR diff as a substitute for what actually landed.

Associate one or more canonical transitions with the merged PR record; do not apply both the PR patch and those transitions to context. Attribution ambiguity is recorded. If the code transition is verified but the PR mapping is uncertain, ingest it as an unattributed transition and reconcile attribution later. Direct pushes and unmapped commits must also enter the ledger so release coverage is complete.

In one logical transition: verify ancestry; compute actual blob changes; update deterministic indexes; invalidate direct/dependent summaries; persist source evidence and change flags; atomically advance the contiguous ingestion watermark. Semantic enrichment is asynchronous. Its failure cannot lose the merge: keep the factual entry and pending or failed enrichment state. Replace stale summary claims with exact-source facts or omit them until regeneration succeeds.

For an out-of-order event, reconcile intervening transitions first. Advance the watermark only over verified contiguous history. Keep separate code-ingestion and semantic-enrichment completeness. Force-reset/non-ancestral branch movement starts a new epoch and requires explicit reconciliation; never splice unrelated history into a continuous journal.

Track migration files, public interface manifests, configuration, dependencies, infrastructure, generated artifacts, and reverts with deterministic selectors where possible. Semantic claims such as “backward compatible” need evidence or remain uncertain. Reverts preserve deployment implications: net-zero code can still require rollout notes if an intermediate version was deployed.

7 Deterministic batched PR review

Before calling the model, host code:

  1. Captures revisions, trusted guidance, and policy.
  2. Fetches a complete changed-file/hunk manifest and exact diff.
  3. Matches mandatory review domains using trusted selectors.
  4. Selects compatible snapshot artifacts and materialized journal updates.
  5. Adds bounded enclosing functions, imports/interfaces, relevant tests, manifests, previous findings, and trusted CI facts using fixed retrieval rules.
  6. Deduplicates by source identity and fits per-layer/total budgets.
  7. Saves the exact serialized prompt, evidence IDs, coverage, exclusions, and omissions.
  8. Makes one structured model request with no tool schemas.
  9. Validates findings and anchors, saves usage/output, renders reports, and evaluates approval in Go.

Source selection is deterministic and configured: changed symbols first; enclosing declarations; direct import/interface relationships; tests selected by supported naming/module rules; a bounded amount of matching documentation. Source readers have path, file-count, byte, index-depth, and time caps. Their output is context preparation, not model interaction.

Prompt layout: trusted task and guidance; repository overview; relevant materialized context; change notes; complete packed PR diff; supplemental exact source/tests/checks; prior findings; host-generated coverage/limitations; JSON output contract. Stable prefix serialization may improve provider caching, but correctness cannot depend on a provider cache hit.

The model returns findings, evidence references, unanswered questions, a review summary, and integer model_merge_risk with evidence-backed rationale. Go compares the effective score with the configured auto-approval threshold. It cannot invoke tools or initiate another call. A request for more information becomes an explicit limitation and human escalation.

Oversize input and retries

Do not silently convert an oversized PR into multiple model review calls. Remove redundant/optional context first. If a required diff/evidence item still does not fit, default to input_incomplete without inference and withhold approval. An explicit report-only partial mode may send one prompt, record every omitted hunk, and still prohibit approval. A later human-triggered rerun is a new run.

Transient transport/rate-limit retries are bounded attempts of the same logical request, not a conversation. Persist attempts and usage; ambiguous provider completion can produce duplicate billing. Invalid/truncated JSON yields an incomplete run; do not start a model repair dialogue. Optional retry of the identical request must be explicitly configured and counted.

Review current PRs in full for the MVP. Unchanged-input reuse is allowed. Changes to relevant code, trusted guidance, context, discussion, or model configuration change the reuse key. Previous findings are included within a separate budget; absence from a new output does not automatically resolve them without validated resolution evidence.

8 Merge risk and configurable auto approval

The single review response supplies an integer model_merge_risk from 1 through 10, with rationale and evidence. One means the lowest estimated merge risk and ten the highest. This is an ordinal assessment, not a probability of failure. The user configures the highest score eligible for auto-approval and the programmatic minimum scores triggered by repository facts. There is no separate model approve/deny vote.

enforced_minimum = max(
    configured_base_minimum,
    every_matching_path_minimum,
    every_matching_change_size_minimum,
    every_applicable_developer_familiarity_minimum
)
effective_merge_risk = max(model_merge_risk, enforced_minimum)

eligible = approval_submission_enabled
           AND valid_complete_review
           AND effective_merge_risk <= configured_auto_approve_max
           AND all_required_checks_and_native_approval_requirements_pass
           AND no_configured_blocking_finding_or_unresolved_required_evidence

The threshold is inclusive: with auto_approve_max: 3, scores 1, 2, and 3 are eligible. A valid score above the threshold means human review, not necessarily that the code must be rejected. All scores and floors are integers 1–10; do not average, sum, round, or clamp invalid model values into a valid score. Missing/malformed model risk means no effective score and no auto-approval, even if deterministic floors can be computed. Publish the known floors as a lower bound.

Compute deterministic facts and floors before inference and include them in the one prompt. After inference, Go recomputes the effective score from trusted configuration and the saved facts. The model can assign a higher score but cannot lower a floor. assess --run re-evaluates thresholds/floors and live requirements without another model call when the saved review and model-rubric/input digests remain valid. A scoring-rubric or relevant evidence change requires a new one-prompt review; changing only an auto-approval threshold does not.

Path rules and wildcard semantics

Each rule has an ID, one or more repository-relative globs, a minimum risk, and optional explanation. Match against the complete changed-path manifest, including files omitted from model input. Additions, modifications, deletions, binary changes, and mode-only changes all count as touched. For renames, match both old and new paths; moving a file out of a sensitive directory cannot evade a rule. Copy records match source and destination where the diff establishes that relationship.

Use a documented slash-based glob dialect: * matches within one segment, ? matches one non-slash character, and ** as a whole path segment matches zero or more segments. Match the whole repository-relative path, case-sensitively, including dot-prefixed paths. Normalize separators only; reject absolute paths and traversal. Reject unsupported glob syntax and invalid patterns at configuration load. No implicit negation or first-match-wins behavior. All matching rules apply and the highest floor wins. A file with no matching rule receives the configured base minimum.

Change size

Calculate size from the complete merge-base-to-HEAD diff before context filtering. Default changed lines are additions plus deletions, without whitespace normalization. A modified line generally counts once removed and once added. Pure content-identical renames/mode changes have zero changed lines but still count toward touched files. An actual rename counts as one changed-file record, with both paths available for matching. Binary files, submodules, and unreadable patches have unknown line counts; apply the configured unknown-size behavior rather than treating them as zero.

Size rules select a named metric and inclusive lower bound, for example changed_lines >= 200 or touched_files >= 15. Every satisfied rule contributes a floor. Optional trusted exclusions for generated/vendor paths must be explicit and visible in the metric breakdown; they do not remove path-rule matches or required review coverage. Unknown factor behavior is configurable as a specified minimum score or human-required. If a metric is only a lower bound, apply already-provable thresholds and the unknown behavior for thresholds not decidable from available facts.

Developer familiarity with affected code

Familiarity measures verified prior authored work in each configured code area, not general tenure, reputation, or whether the developer merely approved a review. An area has an ID and path globs. Match old/new changed paths using the same semantics as risk path rules. Evaluate every touched configured area independently; the least familiar applicable area can therefore impose the highest floor. Work elsewhere cannot dilute that floor. Unconfigured areas use the base minimum and are explicitly reported as unconfigured.

Default metric: number of distinct earlier merged PR integrations authored by the current PR author that touched that area, within a configured lookback window and present in the captured target ancestry. Count each integration once per area. Exclude the current PR, open/unmerged work, mere approvals, and bot-authored changes unless trusted configuration explicitly includes them. Coauthorship and direct commits do not count by default; a future alternative metric must specify its identity and counting rules. Familiarity is a proxy for prior exposure, not proof of competence or correctness.

Use verified provider account IDs and trusted alias mappings. Do not equate an unverified Git email/display name with the author. Resolve renamed historical paths using configured historical globs or verified rename mapping; uncertain mapping is incomplete history, not proven absence. Freeze the as-of time and target revision with the review. For example, zero prior merges in the past 180 days can impose 8, one or two can impose 6, three through nine can impose 4, and ten or more can use the base minimum.

History must cover the requested lookback and tracked ancestry; on a new installation, backfill from the forge/Git before declaring a zero count. Missing permissions, incomplete indexing, unresolved identity, or uncertain area mapping is unknown. The user configures whether unknown familiarity imposes a floor or requires human review. Historical references, counts, evaluated area, window, and completeness are saved as evidence; the journal can maintain this materialized index, but it must distinguish pre-install history gaps from verified zero activity.

Requirements independent of risk threshold

Retain revision validity, required CI results, trusted policy provenance, input completeness, and native branch protection requirements. An acceptable risk score cannot turn an invalid/truncated response, omitted required diff, or stale HEAD into a valid approval. Finding-severity blockers and human-only paths are explicit user policy/native requirements, not hidden score overrides. The model does not supply an additional approval veto: it expresses concerns through the score, findings, and evidence/uncertainty fields.

Coverage is host-owned: each hunk is included, excluded_by_trusted_policy, partially_included, unavailable, or not_included_budget. A PR cannot alter its governing policy. Combine policy layers monotonically: highest floors, lowest allowed auto-approval threshold, and union required checks/human requirements. Validate the full effective policy before reviewing. A model risk score remains a judgment even though floor arithmetic is deterministic.

Immediately before publication, refresh HEAD, target, checks, policy, and applicable author/history inputs. If a refreshed fact changes a model-relevant input, invalidate the review; if only the threshold or independent check state changed, re-evaluate without inference. Bind approval to the reviewed revision where supported, reconcile ambiguous writes, and prevent stale job generations from publishing. Native protections remain necessary where APIs cannot atomically bind every input. Approval never merges or bypasses branch protection.

9 Pre-release assessment mode

Scope and revision capture

release assess takes an explicit prior-release baseline and release candidate, plus repository/branch identity and optional deployment environment. Resolve tags/branches once to immutable commit IDs and record the original names. Default requires baseline to be an ancestor of candidate. Non-ancestral/hotfix history needs an explicit supported comparison mode; the MVP returns an incomplete scope rather than guessing.

An optional artifact/build ID must be tied to the candidate and trusted build provenance. Without it, assess source risk only; do not imply the deployable artifact was checked. If a candidate tag/ref moves, the old report remains historical and is stale for the new candidate. “Previous release” is an explicit configured release/deployment record, never simply the most recent Git tag by timestamp.

Release input package

Assemble compatible base context, verified journal materialization through the candidate, all integrations/direct commits in the release range, net baseline-to-candidate changes, affected-module/interface map, prior review findings with current applicability, candidate check/test/security results, and available operational evidence. Operational evidence includes migrations, dependency/configuration changes, deployment ordering, feature flags, compatibility constraints, rollback/runbook information, environment differences, and known incidents if explicitly supplied through configured sources.

Journal entries since a snapshot and changes since the prior release are different ranges. Include entries necessary to reconstruct candidate context, but identify only release-range changes as new release content. A snapshot newer than the baseline cannot erase already compacted release-range history. Use commit membership, not merge timestamps or branch labels, to identify included changes. Exclude unreleased changes outside the candidate ancestry.

Build an explicit completeness ledger for every release-range transition/PR, relevant risk category, source-change coverage, check source/revision, and missing operational field. Distinguish “verified absent,” “present,” and “unknown.” A missing migration/runbook note is not evidence that no migration or rollback concern exists.

One batched release prompt

Submit one prompt with release identity; architecture/context; complete release change inventory; bounded semantic notes and exact high-impact diffs; dependency and cross-change interactions; prior findings; trusted check/operational evidence; coverage/unknowns; output contract. Context selection is fixed before inference. There are no tools, follow-up turns, per-PR release model calls, or implicit summarization fan-out.

For large releases, retain the complete factual inventory and deterministic risk flags, then add source and semantic detail in deterministic priority order. Record every omitted detail and its category. Required-detail overflow yields insufficient_evidence; do not infer low risk from unseen changes. A user may explicitly request a single-call limited report, but it must carry scope limitations and cannot declare full readiness. Optional journal enrichments already maintained in the background can be reused; the release command does not silently create many model jobs.

Risk and readiness

Return a model-estimated risk with rationale and evidence, then apply programmatic minimums. Use an ordered scale low < moderate < high < critical. Trusted rules define category floors, required operational evidence, blockers, and required human signoffs. Examples: detected schema migration → at least moderate plus migration-plan evidence; explicit incompatible public API change → at least high plus compatibility/deployment-plan evidence; destructive migration with no verified recovery plan → high floor and blocked readiness. Exact rules remain configurable and their selectors must state what they can prove.

effective_risk = max(model_estimated_risk, all_triggered_rule_floors)
readiness = blocked      if a deterministic blocking requirement fails
            incomplete  if required evidence or source scope is unknown
            needs_signoff if configured human signoff is outstanding
            ready_for_engineer_review otherwise

If model output is missing/invalid, retain triggered risk floors as a lower bound, set overall assessment insufficient_evidence, and do not publish a definitive overall risk. An incomplete report can still identify known high-risk changes; it cannot present an unqualified low-risk rating. Readiness is advisory to a release engineer; it neither deploys nor creates approval authority.

Engineer report and release-channel draft

Produce a detailed engineer report and a short channel-ready draft from the same validated result. The engineer report includes candidate/baseline, assessed scope, effective risk and floors, readiness/blockers, interactions between changes, unresolved findings, required actions, migration/deployment order, feature flags, rollback/recovery concerns, recommended smoke tests/monitoring, explicit unknowns, evidence links, and usage/provenance.

The channel draft includes release identity, notable changes, risk/readiness, actionable caveats, expected rollout/rollback considerations, and a reference to the full report. Separate change facts from suggested actions. Do not invent owners, deadlines, test results, customer impact, runbook steps, or a rollback command. Missing details become requests to the engineer. Render the concise draft deterministically from validated fields; no additional model rewrite call. Both outputs are drafts and are not sent to a channel by this command.

11 Trust boundaries and failure handling

No model-callable tools or shell. Host readers use fixed Git argument arrays, validated revisions, path containment, -- path separation, disabled hooks/external diff/textconv, and no submodule execution. Never execute repository code during assembly or indexing. Run required tests in existing trusted CI and consume verified results.

Treat code, PR descriptions, comments, journal semantic notes, and attached runbooks as untrusted input. Keep trusted instructions/policy separate and label source provenance. Findings, recommendations, and release notes cannot execute actions. Do not expose secrets or approval credentials to prompts.

All errors have explicit states. Missing journal ranges trigger catch-up before assembly; if catch-up cannot complete, mark scope incomplete. A provider outage, unreadable blob, stale summary, unsupported check capability, or malformed output cannot become a clean result. Preserve known findings and factual journal records on enrichment failure.

Minimal third party dependencies

Use Go's standard library first. github.com/kzs0/bedrock is the required service telemetry dependency. Pin a compatible release or exact commit after inspecting its current API and changelog. Do not substitute an unrelated library with the same name. The inspected root module declares Go 1.24 and no third-party module requirements; re-check the pinned revision and choose a supported Go toolchain compatible with it.

Canonical configuration is strict JSON, using encoding/json with unknown-field rejection and explicit validation. Use flag for commands, net/http and http.ServeMux for clients/webhooks, database/sql for persistence, os/exec for constrained Git invocations, go/parser and go/ast for Go indexing, html/template for HTML, and testing/httptest for tests. Implement the small documented path-glob dialect locally and test it thoroughly. Do not add an agent framework, CLI framework, router, ORM, forge SDK, model SDK, YAML parser, or a parallel telemetry stack for the MVP. Use typed request/response structs and bounded standard-library HTTP clients for forge/model APIs.

SQLite needs a database driver; select one maintained driver and document its transitive modules, license, and CGO/deployment tradeoff. A tokenizer is an additional dependency only if required for the selected provider's reliable budget enforcement; justify it instead of assuming every model SDK/tokenizer is necessary. Prefer exact supported token counting or a documented conservative bound; do not claim an arbitrary heuristic guarantees a hard limit.

Maintain docs/dependencies.md listing every direct dependency, why the standard library is insufficient, the pinned version, transitive footprint, and upgrade implications. Avoid a rigid dependency-count target that encourages reimplementing cryptography, database engines, or complex protocols. The intended initial direct dependencies are Bedrock and the SQLite driver, with any further dependency requiring a concrete written justification. This is an implementation discipline, not a reason to pause for repeated user approval.

Required Bedrock telemetry integration

Initialize Bedrock once in the CLI/service composition root and pass its context.Context through request handlers and worker jobs. Call the returned cleanup function during bounded graceful shutdown. internal/telemetry contains only application-specific setup, safe attribute helpers, and metric definitions; it must not become a second observability framework.

Use Bedrock Source for worker lifetime, Operation for significant jobs, and Step for internal phases. Register actual errors explicitly because Bedrock operations otherwise succeed by default. Completing a policy evaluation that correctly requires human review is a successful operation with a non-approval decision, not an operational failure. Record malformed model responses, ingestion failures, and failed publication separately.

op, ctx := bedrock.Operation(ctx, "review.run",
    bedrock.Attrs(attr.String("provider", provider)),
    bedrock.MetricLabels("provider"),
)
defer op.Done()
if err := runReview(ctx); err != nil {
    op.Register(ctx, attr.Error(err))
    return err
}

The example uses github.com/kzs0/bedrock and github.com/kzs0/bedrock/attr; verify against the selected pin before implementation. Operation names are static: context.build, journal.ingest, journal.reconcile, review.assemble, review.infer, review.run, merge_risk.evaluate, approval.publish, release.assemble, release.infer, and release.run. Use explicit bounded labels such as provider, phase, outcome, and configured reason code. Run IDs, commit IDs, developer IDs, arbitrary paths, and raw model names/URLs are not metric labels. Put necessary correlation IDs in controlled log/trace attributes instead.

Collect preparation/inference durations, token/cache usage, snapshot health, ingestion lag, journal gaps, familiarity-history coverage, model/enforced/effective risk distributions, threshold decisions, release readiness, retries, and publication outcomes. Use Bedrock's existing metrics/logging/tracing facilities rather than importing a second metrics, logging, or tracing SDK. Avoid duplicate counting from both HTTP middleware and nested operations with the same semantic name.

Use bedrock.HTTPMiddleware and bedrock.NewClient where their recorded attributes are appropriate. Keep request timeouts and context cancellation on outbound requests. Bedrock's HTTP client instrumentation records URL-related attributes; normalize/redact sensitive paths and queries before export, or use a narrow manually instrumented HTTP call when that cannot be guaranteed. Never put credentials, repository content, prompts, full responses, or authorization headers in telemetry.

Service mode may enable Bedrock's metrics/health server on a configured loopback or controlled address; profiling is opt-in. Set server enablement/address/profile settings explicitly rather than relying on ambient defaults. One-shot CLI commands and tests disable listeners unless requested. Managed cloud export is opt-in with explicit destination/credentials; the requirement to use Bedrock does not authorize sending telemetry to an external account. Exporter failures must not alter risk scores, lose journal records, or turn an approval denial into approval. Durable audit records remain in application storage, independent of telemetry delivery.

Acceptance tests verify expected operation names and outcomes, error registration, low-cardinality label policy, shutdown, listener-free CLI/tests, and the absence of sensitive prompt/credential fields. Keep these tests offline using supported local Bedrock facilities and standard-library HTTP test servers.

Use versioned JSON schemas with strict enums and source/evidence validation. The model produces judgments and references; the host adds canonical IDs, coverage, eligibility, risk floors, and publication state. Unknown authorization fields cannot affect decisions.

16 Workers and provider adapters

Persist authenticated event receipt before acknowledging; deduplicate delivery and logical integration identities. Use leases, heartbeats, bounded retries, and per-change generation counters. New PR revisions supersede old review jobs. Merge ingestion is independent and must not be canceled because a review was superseded or failed.

Use separate tracked-branch serialization for contiguous ingestion. Periodic catch-up discovers merges missed during outages, checks direct commits, and reconciles PR attribution. Candidate/review assembly waits for the required journal watermark or explicitly reports gaps. An ancestry mismatch starts a reconciliation workflow rather than advancing a cursor incorrectly.

Forge adapters normalize immutable repository/change identities, pagination, actual merge strategy/range, check producer/revision/conclusion, human approvals, comments, and revision-bound approvals. A check display name alone is insufficient proof; map trusted producer identity and protected CI provenance. Unsupported capabilities produce unknown.

Publish owned comments idempotently with a stable marker and remote ID. Never edit human comments. Revalidate before approval and reconcile ambiguous responses. Source-only release assessment must not imply artifact or environment validation. No release channel connection or recipient lookup is required until outbound posting is explicitly requested.

18 Implementation phases and agent handoff

Phase 1 One prompt local review

Implement Go domain types, strict JSON config validation, Bedrock initialization and operation instrumentation, SQLite/artifacts, exact Git diff/source gathering, deterministic packing/coverage, a counting fake model, one structured-output adapter, and JSON/Markdown reporting. Include the model merge-risk score in the one review response and compute path, size, and familiarity floors in Go. Add deterministic assess without inference.

Acceptance: dependency inventory is present, Bedrock telemetry is exercised without external services or listener leakage, and offline fixtures demonstrate exactly one model completion, zero tools, and zero model calls for approval re-evaluation. A triggered floor overrides a lower model score; threshold eligibility does not bypass a required integrity/check failure. Oversized input cannot silently trigger multiple reviews. Ship a runnable example, not only interfaces.

Phase 2 Snapshots and merge journal

Implement immutable snapshots, Go indexes, bounded background summaries, canonical branch transitions, per-merge attribution, watermark reconciliation, invalidation, and compaction with retained release history.

Acceptance: every merged PR is ingested regardless of review state; missed/duplicate/squash/rebase events are handled; exact landed changes are counted once; unchanged context is shared across distinct reviews; enrichment failure does not lose merges.

Phase 3 Pre-release vertical slice

Implement immutable baseline/candidate capture, release inventory/materialization, completeness ledger, operational evidence adapters, one release prompt, risk floors/readiness rules, and engineer/channel-draft renderers.

Acceptance: one release request includes selected base context and journal plus release evidence, produces an actionable report, never silently ignores history gaps, and does not send a message. Lower model risk cannot override deterministic minimums. Rendering needs no second inference.

Phase 4 GitHub worker and shadow deployment

Implement authenticated events, durable jobs, reconciliation schedules, review comments, trusted checks, and protection diagnostics. Keep actual approval disabled. Exercise merge ingestion and pre-release jobs during provider outages and concurrent updates.

Phase 5 GitLab and approval submission

Add GitLab parity, live policy/check revalidation, revision-bound approval publication, ambiguity reconciliation, and stale-generation controls. Submit mode requires trusted configuration and supported native protections. No auto-merge/deploy/channel posting.

Phase 6 Evaluation and release packaging

Add historical replay, measured performance/quality reports, backup/restore, retention, operational documentation, and release artifacts. Protect scope: no agent loop, hidden chunk model calls, or dashboard unless separately requested.

Instructions to the implementing agent

  1. Inspect the repository and applicable instructions; initialize a Go module only if needed.
  2. Treat this v3 specification as authoritative over earlier approval-vote and exploration/continuation designs.
  3. Build Phase 1 end to end and expose a fake-model call counter in tests.
  4. Keep source gathering deterministic and separate from inference; no tool schemas or tool execution. Use the standard library first and the required github.com/kzs0/bedrock telemetry integration; record justified extra dependencies.
  5. Journal actual integrated changes after every merge, including unreviewed merges, and catch up gaps from Git/forge evidence.
  6. Implement pre-release mode as a first-class command and durable record, not a prose-only TODO.
  7. Use conservative incomplete/unknown states when provider data cannot establish a required fact.
  8. Deliver runnable commands, examples, passing tests, and a clear list of completed behavior and limitations. Do not report placeholder checks as success.
19 Deferred decisions

Incremental partial-PR coverage reuse; embeddings; cross-repository context; synthetic merge/queue review; sandboxed test execution; multi-host storage; optional independent model assessments; dashboard; and explicitly authorized outbound channel posting.
